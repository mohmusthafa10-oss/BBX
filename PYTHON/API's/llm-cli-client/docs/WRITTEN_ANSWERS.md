# Written interview answers

## 1. Is the chat API stateful? How does the model remember my name? (≈150 words)
A standard chat-completions request is stateless: the server generates a response from the messages supplied in that request and does not automatically carry the previous request's message history into the next one. The application creates the experience of a continuing conversation by keeping a local `history` list. Before each turn, it sends the system instruction plus the relevant user and assistant messages again. If I send “My name is Midhun” in one request and then send only “What is my name?” in a separate request, the second call has no reliable access to the first message. The `/stateless` demonstration deliberately makes those two independent requests. The interactive CLI behaves differently because it appends each turn to `history` and resends that list. This is application-managed context, not proof that the underlying model has personal memory. The token-budget manager also visibly removes old turns when necessary.

## 2. Walk me through a tool-calling loop, and where is the security risk? (≈150 words)
The application first sends the conversation and a tool definition to the model. The definition describes the calculator's name, purpose and JSON arguments. The model does not execute Python; it returns a structured tool-call request. My code checks that the requested tool name is on an allowlist, validates the JSON with Pydantic, restricts numeric inputs to a safe range, rejects division by zero, and then executes the calculator locally. The result is sent back as a tool message linked to the original tool-call ID. The model receives that result and produces a final answer. The loop has a strict maximum number of iterations. The main security risk is treating model-generated arguments as trusted instructions. A malicious or manipulated prompt could request an unsafe action, so tools should have least privilege, strict schemas, validation, timeouts and audit logs. Never expose arbitrary shell, filesystem, database or network access just because the model asks for it.

## 3. This chatbot costs too much. Give me five levers. (≈150 words)
First, select a smaller, cheaper model for routine questions and reserve a stronger model for tasks that need it. Second, reduce input tokens: keep the system prompt concise, remove irrelevant old turns, and retrieve only the documents needed for the current question. Third, cap output tokens and ask for concise answers; generated tokens often cost more than input tokens. Fourth, cache stable results such as repeated explanations or reference data, while ensuring user-specific or sensitive answers are not incorrectly shared. Fifth, batch offline workloads where the provider offers discounted batch processing, and monitor actual usage by feature and user so expensive prompts and repeated tool loops are visible. I would also set per-user quotas and alerts, avoid unnecessary retries, and compare quality against cost before changing models. The CLI prints provider-reported token counts and a configurable estimate using published per-million-token rates, making these optimisations measurable rather than guesses.
