I handle rate limiting by checking whether the API returns HTTP 429. When this happens, I first check the Retry-After header. If it exists and contains a valid delay, I wait for that duration instead of calculating my own delay. Otherwise, I use exponential backoff with full jitter. The backoff cap doubles after each failed attempt and never exceeds 60 seconds. Jitter selects a random delay between zero and the cap, helping distribute requests over time. My client allows a maximum of five total attempts. If the server continues returning 429 or 5xx responses, I stop retrying and raise the HTTP error. Other 4xx responses are not retried because repeating an unchanged invalid request usually will not fix the problem.

Exponential backoff increases the waiting time after each failed request, but without jitter, clients that fail simultaneously may retry at the same time. For example, thousands of clients could receive a 503 response and all retry after one second, then two seconds, and then four seconds. This synchronized behaviour can create repeated traffic spikes and put more pressure on an already overloaded server. Jitter adds randomness to each delay, spreading retries across different times and reducing the likelihood of synchronized requests. In my client, I use full jitter, which selects a random wait between zero and the current backoff cap. The cap doubles with each retry and is limited to 60 seconds.

POST requests are not generally idempotent, meaning repeating the same request may create duplicate resources or perform an action multiple times. Before retrying a POST, I would check whether the API supports idempotency keys. I would generate a unique key for the logical operation and send the same key with every retry. The server must recognize that key and return the original result instead of processing the operation again. I would also retry only appropriate failures, use exponential backoff with jitter, respect Retry-After, and limit the number of attempts. If the server does not support idempotency keys, I would first determine whether the operation can be made idempotent or whether the client can safely check the operation's result before retrying.
